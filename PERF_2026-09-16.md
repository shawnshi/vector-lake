## 4. Correctness of the projection

`operational_memory_index` is derived data maintained by SQL triggers on
`operational_memory`, so every writer keeps it in step, including writers outside
`governance_store`. The SQL predicate is an exact restatement of
`_memory_relevance` (a row is dropped only when its relevance is 0, which the
Python scorer drops too) and the SQL window is re-scored with the original Python
oracle, so ordering is preserved rather than approximated. `source_rowid` carries
the store's natural `SELECT *` order as the final tie-break, which is what the
previous stable sort used.

`VECTOR_LAKE_MEMORY_SEARCH=legacy` forces the old full scan; it is the
differential oracle in `tests/test_operational_memory_index.py` (10 query/filter
combinations asserted identical) and an operator escape hatch.

Self-healing: a `PRAGMA data_version` + `Connection.total_changes` guard decides
whether the row-count reconciliation has to run, so an untouched database pays
about 20 µs instead of two `COUNT(*)` scans, and a dropped or short projection is
repaired before the next query.

## 5. Follow-up items 1–3 (authorised 2026-09-16)

### Item 1 — exact n-gram inverted index (`vector_lake/memory_gram_index.py`)

The remaining worst case was `_query_terms` expanding a CJK query into every
character *and* every adjacent bigram, making the SQL scorer `O(rows x terms)`.
Two designs were prototyped before committing:

| Candidate | Long-query latency | Ranking |
|---|---|---|
| FTS5 + bm25 (per-column weights 4/3/1/1) | 240–300 ms | **changes**: legacy top-12 recall only 3/12–12/12 |
| Exact n-gram postings | 0.10–0.58 s | **identical** to the full scan |

The FTS5 prototype was measured and rejected *because it changes the ranking*, not
because of its speed; the n-gram index was measured to touch only **223 253
postings** for the longest realistic query, which pure Python accumulates in
0.12 s — no numpy, no compression dependency. 97 MB of postings replace 25.4 M
SQL rows (which would have needed ~450 MB).

The probe is kept as evidence: `benchmarks/probe_fts_retriever.py` (it builds the
FTS5 projection in `tmp/bench/fts_probe.db` and prints latency and legacy-top-12
recall per query; it never touches the live database).

Layout: `operational_memory_gram(gram, postings)` is a packed little-endian
`uint32` array of `(doc_delta << 4) | field_mask`; `operational_memory_gram_overlay`
holds recent writes as ordinary B-tree rows so applying one document is
`DELETE WHERE doc = ?` plus an insert; `operational_memory_gram_dirty` marks
documents whose base postings must be skipped, which is what makes the merge exact
without storing a document's previous state (and it retires deleted documents too).

Verified on the live corpus: **11 queries × 4 filter combinations, all
byte-identical to the `legacy` full scan**, at 0.098–0.583 s versus 4.66–6.09 s.

Two SQLite behaviours were discovered while building this and are documented in
the code: `OR IGNORE`/`OR REPLACE` inside a trigger that is itself nested in an
upsert raise the UNIQUE violation instead of resolving it (an explicit
`NOT EXISTS` guard is used instead), and a trigger definition therefore has to be
`DROP`ped rather than guarded with `IF NOT EXISTS`, or an upgraded database keeps
the previous body forever.

### Item 2 — dead search projection removed

`operational_memory_search_docs/_fts/_short_fts/_pending/_state/_revision` and
`search_projection_state_v8`, plus the ten `trg_operational_memory_search_*`
triggers that were still maintaining them, were dropped after a verified backup
(`backups/vector_lake_1789575103.db.bak`, 3 622 MB, `integrity_check ok`, row
counts re-read from the backup). Objects 81→66 tables, 72→62 triggers;
49 547 pages (193 MB) returned to the freelist; `integrity_check` and
`foreign_key_check` clean; `operational_memory` (142 117), `claims` (120 339) and
`timeline_events` (9 286) unchanged.

### Item 3 — `index.json` projected into SQLite (`vector_lake/page_index_projection.py`)

The read path parsed the whole 18 MB file once per process and rebuilt a 30 140-edge
adjacency dict on **every** query. Measured with `tracemalloc`: the parse retains
**42.2 MiB** and peaks at **137.4 MiB**; the projected adjacency retains
**9.7 MiB**. Nodes are now fetched per key (a few dozen rows per query) so the
7 178-node dict never exists in memory, and `assemble_context`'s 50-line summary
is a 50-row SQL query.

`index.json` remains the sovereign artifact: `page_index_state(index_mtime,
index_size)` detects an out-of-band rewrite with one `stat`, and the projection
repairs itself. `page_index_edges` carries an explicit `sequence` column because
the two-step personalised PageRank walk is order-sensitive; node dicts,
edge order and the resulting adjacency were verified identical to the previous
in-code build on the live corpus (7 178 nodes, 30 140 edges).

## 7. Residual risk and known limits

1. **Long CJK queries are now sub-second but not free.** 0.43–0.58 s for a
   30-character query, dominated by decoding the posting lists of the common
   single-character grams. It is `O(sum of the postings of the query terms)`, so
   it grows with corpus frequency rather than corpus size, and remains exact.
2. `updated_rank` in the projection is `unixepoch(...,'subsec')` (millisecond
   precision) while the Python oracle uses microsecond floats. Ordering can only
   differ for rows written within the same millisecond; `source_rowid` makes the
   fallback deterministic. Documented in `db_store._OM_INDEX_COLUMNS`.
3. **Write-path cost of the gram index.** The dirty triggers are one guarded
   `INSERT ... SELECT` per projection write; materialisation is deferred, so a
   page ingest pays it on the next read (bounded: 400 documents per call, and
   `AUTO_REBUILD_MAX_DOCS = 2 000` caps the automatic rebuild). A bulk rebuild
   costs ~3 ms/document (431 s for the live 142 117-document corpus) and is an
   explicit operator action: `python cli.py gram-index --apply`.
4. **Storage.** `VACUUM` reclaimed 2 363 MB across two passes and the store is now
   **1 524 MB** with a zero freelist, down from 3 622 MB — while gaining the n-gram
   index (97 MB) and the page projection (~12 MB). The round-2 retention was an
   explicit operator decision, not a heuristic, so the only recovery path is
   `backups/vector_lake_1789597629.db.bak`.
5. The adjacency is built once per process (0.28 s, 9.7 MiB) rather than per
   query. A lazily fetched 2-hop neighbourhood would remove even that, but the
   walk appends zero-mass candidates in adjacency order, so the change would alter
   which zero-weight candidates enter the rerank pool and was not taken.
6. `page_index_edges` duplicates `page_graph_edges` (~1 MB). They are identical on
   the live corpus, but they have different writers, and the read path must depend
   on the sovereign `index.json`, not on that coincidence.
7. **The lost subsystem is now code-less and data-less**: its triggers, its
   registry tables and its 1 346 635 rows of artifacts are gone (section 6). What
   cannot be verified is whether any of that data would have been needed later; the
   backup is the only answer available.
8. Write path: the projection trigger adds **≈118 µs per `operational_memory`
   row** (20 000-row insert: 0.24 s without it, 2.61 s with it). Incremental ingest
   only rewrites the changed claims' memories plus direct conflict peers (tens of
   rows per page), so the per-page cost is ~10–15 ms; the visible cost is a full
   `rebuild_operational_memory` becoming ~17 s slower on the 142 k-row corpus.
   Replacing the inline trigger with a pending-queue trigger would move that cost
   off the write path if it ever matters.
