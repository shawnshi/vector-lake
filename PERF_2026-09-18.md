# Vector Lake read-path audit and remediation — 2026-09-18

Read-only audit of the response performance of the operator-facing surfaces
(`search`, `query`, `timeline`, `graph` and the surrounding core functions), followed by
remediation of the findings under an explicit operator instruction. Section 3 is the
audit, section 5 the applied work, section 6 what is still open.

Section 4.1 records **two corrections to this report's own first version** — both were
wrong in the direction of over-stating the finding, and both are superseded by the
measurements below.

Live corpus throughout (`wiki_pages` 7 923, `claims` 102 117, `operational_memory`
147 231, `timeline_events` 10 294, `index.json` 17.4 MB).


## 3. Audit findings

### F1 — P0: the memory-retrieval fast path was dead in production

`memory_gram_index_report()` on the live store at audit time:

```
ready=True format=2 grams=421496 base_docs=147231 projection_docs=147231
pending=13691 (live=13691 retired=0) usable=False backend=gram
```

The base index was intact and complete, but `gram_index_usable()` requires
`live_dirty == 0`, so **every** memory retrieval refused the index and fell back to the
projected full scan.

Why it was dead, and why it stayed dead:

1. **The repair path is a single background thread that was not running.**
   `maybe_rebuild_memory_gram_index()` is called from exactly one automatic place —
   `watchdog_app.scheduled_lint_loop` (hours 10 and 23) — plus the explicit
   `cli.py gram-index --if-due --apply` and its MCP tool. The watchdog process
   (`scripts/ingest_runner_service.py`, pid 27256 in `.runner_service.pid`) was **not
   alive**, `wiki/.meta/logs/watchdog-stderr.log` stops at 2026-09-17 22:16, and
   `.scheduled_lint_state.json` still recorded `2026-09-17-10`. The 2026-09-18 10:00
   occurrence never ran.
2. **The serving gate and the maintenance threshold are two different predicates.**
   Serving requires `live == 0`; maintenance rebuilds at `REBUILD_AFTER_WRITES = 500`. Any
   live dirty count in `[1, 499]` is *unusable and not due*. On the live corpus the debt
   had reached 13 691, so a rebuild was due and simply never fired.
3. **No read-side actor can repair it.** `AUTO_REBUILD_MAX_DOCS = 2 000` against 147 231
   projection documents, and the incremental drain was deliberately deleted (`3895a5c`).
   The degradation appeared only as an INFO log line per query plus one field in a status
   string that led with `ready=True`.

The 500 threshold itself is a deliberate, documented trade, not a defect: its comment
records that a rebuild costs ~430 s while holding the write lock and refuses every writer
for the duration, and that no saved search time buys back an ingest that failed against a
20 s lock budget. **This audit did not second-guess that choice** (see 4.1).

### F2 — P1: `query`/`assemble_context` runs the expensive memory scan twice

`search_memory_packet_views()` (governance_store.py:1477) called
`search_operational_memory()` twice — active (`top_k=24`, filtered) and history-inclusive
(`top_k=12`, unfiltered) — and each call re-ran `_indexed_memory_candidates` from scratch.
cProfile over 3 `assemble_context` calls: 6 calls, cumulative 4.97 s of 5.79 s.

Measured additivity while degraded: active 1 378 ms + history 1 645 ms = 3 023 ms vs
`search_memory_packet_views` 3 026 ms — exactly two independent scans.

Its docstring claimed the projected scan was shared. It is not, and it cannot be made so
cheaply: the active slice needs the top `active_top_k` rows *among the non-hidden ones*,
and the live corpus carries 26 540 hidden rows of 147 231 (18 %), so any unfiltered window
provably wide enough to contain `active_top_k` non-hidden rows is wider than the filtered
query it would replace.

### F3 — P1: the first embedding call in any process cost ~4.8 s before any network I/O

| Step | Cost |

| `genai.Client(http_options=…)` | **1.31 s** (2nd construction 1.23 s) |

### F4 — P1: `governance_debt` and `trace` decoded the corpus repeatedly

`trace_vector_lake` 7.25–7.73 s, `debt_vector_lake` 11.36–16.71 s:

* `trace`: `_load_db_map` called **6 times** (7.21 s), `load_claims` **twice** (6.55 s), and
  228 296 `json.loads` calls. `ensure_canonical_store_populated()` decoded
  entities + claims + sources — 114 148 payloads, 3.55 s — purely to decide whether the

* `debt`: `compute_debt_metrics` 11.56 s of 12.75 s, driven by 282 164 `json.loads`

### F5 — P1/P2: `lint` spent most of its wall time in `difflib`

`lint_vector_lake(auto_fix=False)` = 29.5–34.5 s wall. The "Similarity Merge (>0.91)"
block at `tool_lint.py:431` constructed **375 283** `SequenceMatcher` objects.

The pair count is linear (a 50-wide sliding window over 7 923 sorted keys), but the
constant is ~17–63 µs per call, so it grows with every ingest. Because
`ratio(a, b) ≤ 2·min/(min+max)`, only **120 210 (32.0 %)** of those pairs could reach 0.91
at all — the other 255 073 (68.0 %) were provably incapable of matching.

### F6 — P2: `doctor` imported every dependency to prove it was installed

`doctor_vector_lake()` = 6.26–6.40 s. The dependency loop used
`importlib.import_module` as an availability probe: `google.genai` 3.19 s,
`logfire.integrations.pydantic` 0.84 s, `bm25s` 0.58 s, `jieba` 0.33 s, `igraph` 0.10 s.

### F7 — P2: the fallback scan is the pathology the index exists to remove

`_indexed_memory_candidates` evaluates `instr()` per term per row: for
`信创 医院 HIS 集成平台`, `_query_terms` returns **17 terms** over 147 231 rows. This is
what F1 exposed on every query, and it is why the n-gram index exists.

### F8 — P3: smaller findings

* `projection_report` 0.87 s: parses `index.json` (0.54 s, 133 MiB peak, 40.5 MiB retained).
* `search(page)` reads each returned page body from disk (`top_k` reads).
* Store: 2 050 MB with a 96 469-page freelist (395 MB) at audit time.
* `graph` is **healthy**: `json.load(index.json)` 0.54 s + `_build_graph_payload` 0.40 s
  (peak 11.7 MiB) + `json.dumps` 0.07 s for a 10.2 MB payload; `_build_page_graph` is the

### F9 — No finding: `timeline` is healthy

`search_timeline` 0.04–0.30 s across every filter combination with no errors (entity only

### 6.1 Two interactions this session exposed

1. **A gram-index rebuild blocks the projection drain, and the drain re-dirties the
   index.** The rebuild holds the write lock for its whole transaction, so the outbox
   worker failed closed every cycle (`Could not acquire the Vector Lake write lock within
   20s … database is locked`) and then logged `Outbox Consumer Halted. Entering 60s
   cooldown` — a retrying halt, not a terminal one. The drain stopped at 1 110 pending
   during rebuild #1 (22:49→22:57) and at 610 during rebuild #2 (the 23:00 scheduled
   occurrence). Meanwhile the drain's own writes are what re-dirtied the index
   (0 → 14 682), so the two are in tension by construction: **backlog recovery and index
   freshness cannot both make progress at once.** Settling it needs one ordered pass
   (drain to zero, then rebuild once), which is what left the final state clean.
2. **`VACUUM` and the rebuild undo each other.** `VACUUM` reclaimed 391 MB at 22:47; the
   rebuilds at 22:49, 23:00 and 23:22 re-inflated the file to 1 962 MB with the same 384 MB
   freelist, because each rebuild rewrites the whole gram table. `VACUUM` is therefore only
   durable if it is the **last** maintenance step; it was re-run at 23:36 and the store now
   rests at 1 571 MB with a zero freelist.

## 9. Why the ingest runner was not running, and the fix (2026-09-19)

### 9.1 Diagnosis

The runner was not "never started" — it was **started and then killed with its launcher**, and
nothing owned its lifecycle afterwards.

| Evidence | Finding |
|---|---|
| `runtime/runner_supervisor.json` | supervisor pid 25232, child pid 26088, `status=running`, `model_command="python scripts/ingest_model_pi_subagents.py"`, `shadow=false` — it was resident and writing real pages |
| `runtime/runner_status.json` | child started 2026-09-17T14:11:07Z, **last batch 14:16:13Z**, `cycles=2`, `model-failed=1` |
| `(Get-CimInstance Win32_OperatingSystem).LastBootUpTime` | **no reboot** (uptime 2 d 10 h; booted 2026-09-16 20:29) |
| `watchdog-stderr.log` | last line 2026-09-17 22:16 |
| `.runner_service.pid` | pid 27256, written 2026-09-17 21:57, process gone |
| `grep subprocess vector_lake/watchdog_app.py vector_lake/ingest_worker.py` | **no spawn at all** — the watchdog never started the runner |

So: the watchdog and the runner both stopped within the same minute (22:11–22:16 CST) with no
reboot, i.e. they were terminated as a process tree when the agent session that launched them
ended. Because only `watchdog_sync.py` had a launcher skill and the README required the runner
as a second *manual* resident, the result was a pipeline that published packets into
`awaiting_subagent` and never reported a fault — 32 unfinished jobs and 29 un-ingested raw
files for 34 hours. A 3rd contributing fact: the model seam had already failed once with
`model runner exited 5: model seam: child JSON invalid: Expecting ',' delimiter: line 1
column 4531` (a 4 KB page payload the seam could not serialise back).

### 9.2 Fix

New `vector_lake/runner_supervision.py`: the watchdog now **spawns and supervises**
`scripts/ingest_runner_service.py` as a child process.

* **Boundary preserved.** The model call still happens in a child of the runner, never inside
  the runtime process — this module owns only the supervisor's lifecycle.
* **Adoption, not duplication.** Before spawning, the loop asks the instance lock whether a
  supervisor is already live (a hard kill cannot run the watchdog's shutdown hook, so its
  supervisor is orphaned by design — it puts itself in its own process group so a control
  event cannot reach a mid-flight model call). An existing supervisor is adopted and reported.
* **Restart ladder** (5/15/60/300 s) for real exits; a sub-10 s exit — a duplicate, a missing
  prerequisite — polls once a minute instead, so this cannot become an error storm.
* **Switches** (all documented in the README configuration list): `VECTOR_LAKE_RUNNER_AUTOSTART=0`
  keeps the health warning without the autostart; `VECTOR_LAKE_RUNNER_MODEL_CMD` overrides the
  model seam; `VECTOR_LAKE_RUNNER_SHADOW=1` makes the supervised runner report-only. Defaults
  reproduce **this host's own recorded configuration** (real writes, the documented model
  command), so the change restores the previous intended state rather than expanding it.

`scripts/ingest_runner_service.py` gained a **single-instance lock**
(`<meta>/runtime/.runner_service.lock`) — a hand-started supervisor and the watchdog's cannot
become two consumers of one task queue — and a **60 s heartbeat**, because the child runner is
long-lived and a supervisor that wrote only on transitions would have reported itself
`runner_supervisor_stalled` 40 minutes into a healthy run (`VECTOR_LAKE_RUNNER_STALE_SECONDS`
default 2 400). A defect in the first version of this change was found and fixed during
verification: the losing supervisor wrote `status="duplicate"` **with its own pid** into the
shared `runner_supervisor.json`, so health would have shown a dead pid as the owner.

## 10. Audit: watchdog and auto-ingest — completeness, stability, performance (2026-09-19)

Read-only audit with the daemon running live. Verdict up front: **the pipeline works end to
end when a consumer exists, but four completeness gaps and three stability gaps are real**,
one of them privacy-relevant. Performance is acceptable for a background compiler.

### 10.1 Completeness

**C1 (P0) — no periodic catch-up scan.** `prepare_ingest_batch` (the only thing that turns a
raw file into a job) is reachable from exactly two places: a raw filesystem event
(`RawWatchdogHandler` to `sync_vector_lake`) and a manual CLI/MCP call. Nothing sweeps on a
schedule. Measured consequence: of the **28 un-ingested raw files, 8 have no job row at all**
— 5 carry an in-flight marker written at 23:28 yesterday with no job behind it, and 3 are
`privacy/Diary/*.md`. No raw file has been written since 22:19 yesterday, so no scan has run
since; those 8 are invisible to the runner and stay invisible until an unrelated raw event
happens to fire. A lost, cancelled or never-enqueued task therefore has no automatic recovery
path.

**C2 (P0, privacy) — the diary guard is at one entry point only.** The documented invariant is
"diary text is never ingested into the lake" (`RawWatchdogHandler.handle_event`,
`tests/test_watchdog_diary_removal.py`). The guard is `if "privacy" in filepath and "Diary" in
filepath: return` — inside the *event handler*. The batch scan that the same handler then calls
has no such guard: `DEFAULT_EXCLUDE_PATHS = ("stocks/", "garmin/", "personal-insights/")` and
`config.json` adds none, so `raw/privacy/Diary/2026-Q{1,2,3}.md` pass the hidden-file,
exclusion and extension filters. An event on **any other** raw file — or one `cli.py sync` /
MCP `prepare_ingest_batch` call — therefore enqueues the three diary files for real ingestion.
The existing test mocks `sync_vector_lake`, so it cannot see this.

**C3 (P1) — stale-task expiry is manual-only.** `expire_stale_subagent_jobs` (default
`max_age_seconds=86400`) is reachable only from `cli.py ingest-tasks --expire-stale` and the MCP
tool; neither the watchdog nor `ingest_worker` calls it. Evidence: 27 jobs aged **33.8 h to
184.6 h** (created 2026-09-11 to 2026-09-17) were still open until a consumer appeared.

**C4 (P2) — partly orphaned in-flight markers.** `prepare_ingest_batch` truncates to
`batch_size`, marks that **whole** batch in-flight, and only then enqueues. The enqueue loop's
`except` clears the marker of the file that raised and re-raises, aborting the loop, so every
file marked after the failure keeps its marker with no job for the 1 h
`INGEST_IN_FLIGHT_TTL_SECONDS`. That is the shape of the 5 marker-only files in C1.

**C5 (P1) — a missing consumer discards work rather than parking it.** 8 jobs carry
`Ingest task expired three times without ever being claimed (no host relay consumer is
running); cancelled so …`. Expiry-as-cancellation is the designed answer to an absent runner,
so a dead runner loses sources silently instead of queueing them.

### 10.2 Stability

**S1 (P0) — no liveness supervision of the loop threads.** The main thread rewrites the
aggregate `updated_at` every 30 s, and both consumers of that file — `runtime_health.py:258`
and `tool_doctor.py:201` — inspect only `components[*].status`, never a component's
`updated_at`. So `max_watchdog_age_seconds=120` cannot fire while the process lives, and a loop
thread that dies leaves its last status ("idle") looking healthy forever. A plausible death path
exists: `index_worker_loop`'s `finally: close_connection()` runs after the per-iteration
`except`, so an exception there escapes the loop and ends the outbox consumer permanently.
Nothing checks `thread.is_alive()`, and there is no supervisor of the watchdog itself.

**S2 (P1) — a poison task is retried hourly, forever.** Live example at 07:26 today:
`Error finalizing ingestion: Strict Naming Violation: 'Concept_Formula_售前技能评估四维十二项评分.md'
must match pattern [Type]_[MainName]-[SubName].md`, with the runner at `errors: 2,
consecutive_failures: 2`. A rejection leaves the job in `subagent_processing` with its 1 h
lease, `claim_ingest_tasks` re-claims the oldest first (`ORDER BY created_at ASC`), and there is
no attempt cap, no dead-letter state and no escalation — so a deterministic model/validation
mismatch spends one model call per hour indefinitely. The runner's 5-failure cooldown and the
`_ingest_finalization_proven` duplicate check both work; neither bounds this.

**S3 (P1) — a failing scheduled occurrence retries unbounded and takes the maintenance chain
with it.** `last_occurrence` is only advanced after success, so a failure retries every 30 s,
each attempt holding `global_task_lock` for the whole lint. The WAL checkpoint, gram rebuild and
backup retention sit *after* the lint call in the same block, so a persistently failing lint
also stops the only periodic WAL truncation and the retention pass.

**S4 (P2, semantics) — `halted` is the wrong word for a self-healing state.** A transient DB
lock loss makes the outbox report `halted`, which `watchdog_status` ranks at priority 3 (above
`error`) and which the aggregate takes as the worst component. The whole daemon then reads
"halted" and `/doctor` plus health raise `watchdog_unhealthy` for a condition that recovers by
itself (observed 23:26–23:34 during the gram rebuilds).

**S5 (P1) — one global lock serialises the drain with all maintenance.** Observed directly: the
projection drain stalled at 1,110 and again at 610 pending while the two gram rebuilds held
`global_task_lock`.

**S6 (P2, introduced by the section 9 change) — the `runner` component's age is never
refreshed.** The supervision loop writes once when it spawns and then blocks in `child.wait()`,
so `components.runner.updated_at` froze at 23:22:41 while the supervisor's own file
(`runner_supervisor.json`) correctly heartbeats every 60 s. Harmless today only because of S1
(component age is not read) — but it is the same pattern this section calls out.

**S7 (P3) — a sink without a reason.** The `C7` branch ("leave it to the runtime") counts an
unreadable packet as an error without writing anything to `stats["last_error"]`, so one of the
two live errors has no recorded cause.

**No finding — backup retention is correct.** The 23:00 occurrence logged no removal because the
directory held exactly 3 entries (the `keep` bound), grouped as one entry for the
`.db.bak`/`-wal`/`-shm` triple; the 4th entry (`premerge-…`, 07:22 today) makes 1 prunable
(2.13 GiB) for the 10:00 run. `doctor`'s `backup_footprint_over_bound` name is misleading — it
fires on count>keep, not on bytes>bound — but the logic and the plan are right.

|---|---|---|
| Watchdog CPU while ingesting | **1.11 %** of one core (+ runner 0.50 %, supervisor 0.02 %) | acceptable |

### 10.4 Recommended order

1. **C2** first — it is the only finding with a non-performance consequence. Either give the
   batch scan the same `privacy/Diary` decision (one owner, both entry points) or move the

2. **S1** — a liveness check that turns a dead loop thread into a visible status (component
   `updated_at` age, or `thread.is_alive()` in the heartbeat), so S2/S3 failures cannot hide.
3. **S2** — an attempt cap or dead-letter state per job, so a deterministic rejection stops

4. **C1 + C3** — one periodic catch-up sweep in the watchdog (scan for un-ingested raw files and

5. **S3 + S5** — bound the scheduled occurrence's retry, and take the maintenance steps out of

6. **S4 + S6 + S7** — reporting hygiene: a distinct status for "recovering", a heartbeat in the

7. Throughput (`--limit`, `--interval`) is an operator decision rather than a defect.

## 12. Rebuild outside the global lock, and the throughput constant (2026-09-19)

The last two items of the section 10.4 list. **1063 tests pass** (1053 before).

### 12.1 What the rebuild cost, measured before touching it

Phases of the shipped single-transaction rebuild, timed on a `VACUUM INTO` sandbox copy of the
live database (never the live file):

| Phase | Time | Share |
|---|---|---|
| staging (projection read + gram extraction + insert) | **436.1 s** | 94 % |
| delete base + change markers | 0.1 s | 0 % |
| pack staging into the base | 28.7 s | 6 % |
| record state | 0.0 s | 0 % |
| **total** | **464.9 s** | |

So the whole write-lock hold was the staging pass, and that is what got batched.

### 12.2 The change

`rebuild_memory_gram_index` is now three phases, none of which holds the write lock for long:

1. **Staged postings + a per-document fence**, one committed transaction per `batch_docs` batch.
   Each staged document records a `sha256` of the exact bytes it was read from.
2. **Packing** into a private next-generation base table, one transaction per chunk of *whole*
   gram groups (the chunk bounds come from the ordered gram list, so no group is split).
3. **Publish**, one short transaction: the fence, a `DROP` + `RENAME` swap, and the state row.

The single transaction was load-bearing, and what replaced it is the fence rather than a lock:
a change marker is dropped only when the document still digests identically to what was staged.
Anything written during the rebuild keeps its marker, so `gram_index_usable()` stays false until
a quiet rebuild -- the same honest degradation, without blocking every other writer.

The scheduler no longer wraps the rebuild in `global_task_lock`; that mutex made a scheduled
maintenance step an outage for the mutation path (observed twice on 2026-09-18: the drain froze
at 1 110 then 610 pending rows and logged lock failures throughout).

### 12.3 Measured result

Sandbox, 147 280 documents / 26 294 784 postings, with a concurrent writer committing every 2 s:

| | before | after |
|---|---|---|
| wall time, idle database | 464.9 s | **149.4 s** (3.1x faster) |
| longest write-lock hold | **436 s** (the entire build) | **2.20 s** |
| concurrent writer commits during the rebuild | 0 (refused) | **55, 0 failures** |
| waits longer than 5 s | n/a | **0** |
| published base | reference | **byte-identical** (`sha256 51527d9d…`, same 421 575 grams / 105 179 136 blob bytes / state row) |

Live corpus, with the real drain running concurrently: 573.5 s total
(`stage=301.0 s, pack=264.0 s, publish=0.5 s`), the fence kept **1 315** documents written during
the rebuild and cleared 9 492, and the watchdog log recorded **zero** lock failures in the
window. The index reports `usable=False` afterwards because 380 of those kept documents were
written after their batch was staged -- which is the designed degradation, not a fault.

Two measurement-driven corrections along the way, both worth recording because they were
counter-intuitive:

* A compound keyset (`gram > ? OR (gram = ? AND doc > ?)`) plans as a **full scan**, and one scan
  per chunk of a 26 M-row table made the first batched version 2.4x *slower* than the code it
  replaced (1 101 s). Range bounds on the leading key column plan as index searches.
* The staging payload is built in document order while the staging table is keyed `(gram, doc)`,
  so unsorted batches scatter across b-tree leaf pages: one 360 000-row batch into a 5 M-row
  tree costs **3.32 s unsorted against 0.66 s sorted**. Sorting the batch is what took staging
  from 436 s to 111 s and the longest hold from ~21 s to 2.2 s.

### 12.4 The throughput constant

`--limit 2` with `--interval 120` (limit was 1, interval 180), set as the supervision default, in
the supervisor's own default, and in the README runbook. That is ~40 files/hour instead of ~14
(§16.1 records the change from 1 to 2 and why); a batch that finds no work costs one claim query.

The two passes are the point: **a gram rebuild re-inflates the file by ~510 MB** (its staging
tables and superseded base), so `VACUUM` only holds if it runs *after* the rebuild. The first

Two backup roots, and only one is managed: retention prunes `wiki/.meta/backups` (now 3.2 GB);

verified recovery points from this session live.

### 13.2 The linter never needed the mutex

`global_task_lock` had exactly two users: the outbox consumer's batch and the scheduled
occurrence (graph refresh + lint). Its effect was to serialise a ~13 s read against the mutation
path, and the occurrence ran twice a day.

Two measurements decided the fix:

* Under `PRAGMA query_only=ON`, `lint_vector_lake(auto_fix=False)` **completes a 13.1 s scan of the
  live corpus without attempting a write** -- every writer in it is guarded by `auto_fix`, so the
  scheduled call is read-only.
* In the same probe, `refresh_graph_topology_if_dirty()` raised `attempt to write a readonly
  database` **immediately**: it opens its write transaction *before* deciding whether anything is
  dirty, so it genuinely holds the database write lock for its whole body.

So the mutex now covers only the graph refresh, and the lint runs outside it. Live verification,
from the daemon's own log:

```
09:57:59  Triggering Scheduled Autonomous Auto-Lint ...        <- lint starts (13 s scan)
09:58:06  Outbox batch completed: {'claimed': 7, 'completed': 7} <- 7 s INTO the lint
                                                                   0 lock failures in the window
```

Before this change that batch could not have run until the lint finished. What remains serialised
is the graph refresh (a writer, correctly) and the ~16 s lint is no longer a stall for the
projection drain.

A smaller follow-up is visible in the second measurement: the graph refresh opens a write
transaction even when nothing is dirty, so every occurrence takes (and holds) the write lock for
no reason. Hoisting the dirty check above the transaction needs a cheap pre-check that
`is_graph_dirty` currently cannot give without loading the 17 MB `index.json`, so it was left as
a documented follow-up rather than guessed at.

### 13.3 What an interrupted rebuild leaves behind

Killing the daemon mid-rebuild (done deliberately while restarting) left three things, all
self-healing but worth recording:

* the rebuild's **scratch tables** (`operational_memory_gram_stage`, `_stamp`, `_new`) still in the
  schema -- the next rebuild drops them first, so this is bounded waste, not corruption;
* a **1 554 MB WAL**, because the rebuild defers its auto-checkpoint and the process died before
  the post-rebuild `TRUNCATE`;
* the base **unchanged** (the swap is one transaction, so there is no half-published state).

The next occurrence reclaimed all of it: rebuild at 10:03:32, `WAL checkpoint (TRUNCATE)
completed`, scratch tables gone, occurrence recorded as
`{"last_occurrence": "2026-09-19-10", "outcome": "completed"}`.

## 14. The content rule the model kept breaking, and a source-level dead letter (2026-09-19)

### 14.1 The rule was never stated where the model could read it

The validator requires ``categories`` to be **a list with exactly one element**

macro-domains"* -- which a model satisfies with `categories: Healthcare_IT` or with a two-element

nowhere in the form the *author* sees it.

| validator message | `categories must be a list with exactly one domain.` | the same sentence plus what arrived -- `Received a list of 2 element(s): [...]`, `Received str 'Healthcare_IT'`, `Received no value` -- because the recorded reason is all an operator sees |

### 14.2 A dead letter for a source, not just for a job

"Bounded attempts" bounded one *job*. Each re-dispatch began with a fresh budget, so a source whose
content cannot pass kept cycling: three model calls, terminal, re-dispatch, three more. The attempt
budget was doing its job on the job and nothing at all on the source.

`ingest_abandoned_sources(filepath, file_hash, reason, terminal_jobs, abandoned_at)` records the
**content** after the third deterministic terminal failure. The key is `(filepath, file_hash)`, so a
corrected file is dispatchable again with no operator action; only deterministic failures land there
(a transient one is still released for retry). The scan skips abandoned sources and says so in its
message; `cli.py ingest-tasks --abandoned` lists them with reasons and
`--clear-abandoned [FILE]` re-enables dispatch, mirrored as two MCP tools.

### 14.3 Two further defects found while verifying this

Both were found by watching the live queue rather than by reasoning, and the second was mine:

**A `finalized` job for an unpublished source made the scan's enqueue a no-op.** `DHWB-20260913.md`
had a `finalized` job from 2026-09-17 while having no page and no ledger row. `replace_terminal`
correctly refuses to supersede *finished* work, so `enqueue_job` returned that finished job's id: the
scan counted the file as "enqueued", marked it in-flight, dispatched nothing, and the next sweep
released the marker and repeated -- a 12-minute loop producing nothing, which is exactly the pattern
measured in the log at 10:13 and 10:25. `enqueue_job(..., supersede_finished=True)` now exists for
the one caller that has *established the source is unpublished* (the scan reaches it only past
`raw_is_published`), and the collision is logged: the page and the ledger disagree, which an operator
should know.

**My own `replace_terminal` superseded jobs that were still in flight.** It asked "is this job not
finished", which is also true of `queued`, `awaiting_subagent` and `subagent_processing`. The live
queue at 10:50 showed six sources with **three to four concurrent jobs each** -- three to four model
calls for one file. Restricting it to `failed`/`cancelled` (`INGEST_JOB_TERMINAL_FAILURE`) fixes it;
the duplicates already created drain as cheap `duplicate` verdicts, which are closed *without* a
model call by `raw_is_published`, and the count fell from 16 to 11 while the fix was being verified.

### 14.5 What is deliberately not done

* The prompt now *states* the rules; it cannot make a model obey them. That is what the dead letter is
  for: the next source that keeps failing deterministically stops costing model calls and becomes
  visible with a reason instead of looping.
* `categories` could also be coerced (a bare string wrapped into a list) instead of refused. That
  would silently accept a payload the author did not intend, and the rule is a purpose-contract
  decision rather than a formatting detail, so it stays a refusal.

## 15. Closing the ledger gap: published sources with no record (2026-09-19)

After the content-rule fix the audit still reported one un-ingested source, and it was the
interesting kind: `raw/医疗信息化/推动健康中国建设取得决定性进展有关情况.md` has a page
(`Source_医疗信息化-推动健康中国建设取得决定性进展有关情况-92f53b7a.md`, created 2026-09-14) that
**declares that exact raw path** in `sources:`, but no `processed_files` row.

That state is documented in `_already_published`'s own docstring -- "a source ingested while the
ingest pipeline was stalled has a page but no row" -- and the skip it produces has a second
consequence the docstring does not mention:

* the ledger is wrong, so every count built on it reports a permanent backlog (the reason this
  audit was run);
* **a later edit to that source is never ingested**, because the published branch runs *before*
  the hash comparison that a ledger row enables.  A ledgared source whose hash changes becomes
  pending; an unledgared one is skipped forever.

### 15.1 The decision, and the evidence it uses

`_published_source_verdict()` now returns one of three answers for a source the publication check
calls published:

| Verdict | Condition | Action |
|---|---|---|
| `record` | a page **declares** this raw path, and the raw file's mtime is not newer than that page's `created` date | write the missing `processed_files` row (with the current hash) and skip |
| `stale` | declared, but the raw file is newer than the page | do **not** record; fall through as pending so the edit is ingested |
| `skip` | only the loose name signal matched, or no usable date | skip as before |

The declaration signal is the authoritative one (`_declared_raw_keys`'s docstring says so); the
name signal is over-eager by design for duplicate prevention, which is exactly why it may not be
used to retire a source *permanently*. No raw hash is stored on the page, so the content question
is answered by the page's `created` date against the file's mtime -- and the ambiguous direction
resolves to re-ingesting rather than retiring.

The row is not a rubber stamp: it carries the content hash, which is what makes the *next* edit

### 15.3 Tests

Eight in `tests/test_ledger_reconciliation.py`: the index carries the page and its date; an

### 15.4 Still open

  mtime comparison decides; nothing reconstructs which content the page was built from, because

* **A claim in the first version of this section was wrong and is withdrawn.** It said a

## 16. Operator batch, the REST transport, and an independent review (2026-09-19)

Seven operator decisions landed in one batch; an independent reviewer then found three real defects
in the result, all fixed here. **1 130 tests pass** (1 115 before), and `ruff` reports the same 35
findings in the touched files as `HEAD` does.

### 16.1 Throughput: `--limit 2 --interval 120`

Set as the supervision default, the supervisor's own default, and in the README runbook. `--limit 2`
means two task packets in flight per cycle, so a burst drains ~40 files/hour instead of ~14.

### 16.2 The 11 terminal-failed jobs are closed

They had spent their attempt budget and their sources were all in the ledger (verified: 0 of the 11
un-ledgered), which is why `doctor` reported `[FAIL] Ingest Jobs: terminal_failed:11` for work that
was in fact finished. `cli.py ingest-tasks --close-terminal-failed` marks them `superseded`, and it
**refuses** to close a job whose source has no ledger row -- that one is genuinely unfinished and the
abandonment rule decides its fate. Result: `[OK] Ingest Jobs: queued:0 awaiting_subagent:0
terminal_failed:0`.

### 16.3 The raw hash is stamped on the Source page at finalize

`_stamp_source_hash` injects the packet's `hash` into the canonical Source page's frontmatter on the
write path (not by the model: the value has to be the packet's own). `_declared_raw_sources` now
carries it, and `_published_source_verdict` **prefers it over the date heuristic**: a matching hash
is proof the staged content is current, a different one is proof it changed. Legacy pages without a
stamp keep the date fallback. Verified end to end through `finalize_ingest` (the page is written
with `source_hash`, the other fields and the body intact).

### 16.4 The embedding transport no longer pays for the SDK

| path | wall (first call, fresh process) | ``google.genai`` imported |
|---|---|---|
| SDK | 8.33 s | yes (3.5 s import + 1.3 s client) |
| **REST (new default)** | **1.54 s** | **no** |

Both returned **bit-identical** vectors for the same text (cosine 1.00000000), so this is a
transport change, not a behaviour change. Cold CLI `search`: **3.34 s** (REST) against **7.96 s**
(`VECTOR_LAKE_EMBEDDING_TRANSPORT=sdk`) -- the same subprocess, differing only by that switch.
The rate limiter, budget deadline, retry classification and response validation are shared with the
SDK path, and `VECTOR_LAKE_EMBEDDING_TRANSPORT=sdk` forces the old behaviour. Prewarming now skips
itself on the REST path, because it exists to hide the client construction the REST path never does.

### 16.5 What the independent review found, and what was done about it

A fresh-context read-only reviewer was given the five invariants of §11–§15 to falsify. It confirmed
the rebuild's fence ("never publishes a stale base for a dropped-marker document"), then reported:

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | major | **`embedding_backfill` still built the SDK client unconditionally** -- so the bulk path paid the 4.8 s import and, on a host without `google-genai`, raised `ImportError` before `_request_embeddings` could post over REST | the client is now transport-scoped (`embedding_scheduler.embedding_backfill`) |
| 2 | major | **A superseded `failed` job stayed claimable.** Clearing its idempotency key left it `failed` with unspent retries, and `claim_pending_jobs` claims `failed` while `retries < MAX`, so the old row *and* its replacement were both dispatched -- two model calls for one source, in the very path added to remove double dispatch | the superseded row is now marked `superseded`; a superseded *finished* row keeps its status, because it was already unclaimable |
| 3 | major | **A loop that returns by design was treated as dead**: `catch_up_loop` returns at `VECTOR_LAKE_CATCHUP_INTERVAL_SECONDS=0` and `runner_supervisor_loop` returns on an opted-out host, both documented configurations -- yet they were restarted on every heartbeat and, once the budget was spent, reported the whole daemon as `error` | `thread_supervision.finish(name, reason)` lets a loop declare its return as intended; such a loop is reported as `finished by design`, never restarted |
| 4 | minor | §12.4 still described `--limit 1` | corrected in place (§12.4, §12.3, §11.1) |
| 5 | minor | A name-signal-only skip left a source invisible on every scan, while the docstring implied it stayed reachable | the scan now counts name-only skips *apart* from undated declarations and reports them in its message; the docstring states the trade |
| 6 | nit | The fence's digest pass runs under the write lock, so a fully dirty corpus could hold it | measured: 5.9 µs/row, **0.9 s extrapolated with all 146 642 documents dirty** -- inside the 20 s writer budget, so no change |
| 7 | nit | §12.6 still said `global_task_lock` serialised the lint, which §13 had already removed | corrected with a pointer to §13.2 |

### 16.6 Still open (unchanged by this batch)

* **The graph refresh opens a write transaction before deciding anything is dirty** (§13.2). Cost
  measured at ~0.6 s plus the write lock, twice a day. A sidecar stamp would remove it but adds a
  second source of truth about `index.json`, and a re-read restructure would add a second code path
  through the projection; neither is worth 1.2 s/day, so it stays documented rather than guessed at.
* **`trace` (4.2 s) and `debt` (5.2 s) still decode every claim.** `_load_db_map` memoisation is the
  obvious lever, but callers mutate the returned payloads, so a cache would need a copy-on-return
  discipline; the structural fix is projection columns for the claim fields those two read.
* **`projection_report` (0.87 s) and `check_duplicate_entity` (1.02 s)** are advisory diagnostics
  called on request; `projection_report`'s whole purpose is to compare against the sovereign
  `index.json`, and swapping `check_duplicate` to the page projection needs a per-field audit of
  what it reads. Left as measured, bounded costs.

## 17. Residual risk and limits

1. Latency numbers are from one machine and one corpus state; SQLite scan times varied by
   up to 2× between processes for the same statement, so ratios are more reliable than
   absolute values.
2. The rebuild cost (514.7 s measured) and the write-lock exposure it implies were measured
   once; the `REBUILD_AFTER_WRITES` trade was not re-evaluated.
3. The write/ingest path was not benchmarked: this session mutated only the index. The
   previously documented ~118 µs/row trigger cost and ~10–15 ms/page ingest cost remain
   unverified here.
4. The correctness oracle for every fix is the test suite (970 pass) plus the specific
   differential checks named in section 5 (full-decode equality for the memory aggregates,
   `PYTHONHASHSEED=0` byte equality for the lint findings). No independent reviewer was
   involved.
5. `graph` was measured, not optimised; `_build_page_graph`'s 1.77 M `dict.get` calls are a
   known linear cost that will need attention only if the edge set grows much larger.
