# Vector Lake architecture review — 2026-09-17

- Scope: `vector_lake/` runtime (49 modules), `scripts/`, MCP/CLI surfaces, and the live
  `C:/Users/shich/MEMORY` state (wiki, `.meta`, SQLite).
- Method: read-only code walk, AST import-graph/SCC analysis, live-DB probes, full test
  suite, hot-path benchmark. **No file in the repository was modified by this review.**
- Baseline measurements taken in this session (`tmp/bench/bench_stage0-baseline.json`,
  `tmp/audit2/pytest_baseline.txt`).

## 0. Executive summary

Vector Lake's read path is in good shape: 450 tests pass in 24.4 s and every operator-facing
read surface is sub-second on the live corpus. The remaining risk is concentrated in three
places, in this order:

1. **Concurrency** — the SQLite write-lock retry has no deadline and can park a call for
   ~31 minutes while the process looks hung.
2. **Durability** — no write path calls `fsync` before `os.replace`, so a crash can leave a
   truncated or zero-length canonical file.
3. **Lost subsystem** — the working tree is a *subset* of the system that produced the
   persisted state. 34 modules that existed on 2026-09-07 are gone, and the artifacts they
   wrote are still on disk with no producer and no consumer.

Item 3 has no clean fix and is the largest architectural risk in the project.

## 3. Findings

Severity: P0 = correctness/availability risk now, P1 = real defect with a bounded trigger,
P2 = resource/efficiency, P3 = hygiene.

### F1 — P0 — the write-lock wait has no deadline (reliability)

`vector_lake/db_store.py:82-108`

```python
conn = sqlite3.connect(str(db_path), timeout=30.0, check_same_thread=False)  # line 60
...
max_retries = 60
for attempt in range(max_retries):
    try: conn.execute("BEGIN IMMEDIATE"); break
    except sqlite3.OperationalError as e:
        if "database is locked" in str(e) and attempt < max_retries - 1:
            time.sleep(0.5 + random.random()); continue
        raise
```

`timeout=30.0` is the SQLite busy timeout, so **each** attempt already blocks inside SQLite
for up to 30 s before raising. The loop then retries 60 times with a 0.5–1.5 s sleep:

    worst case ≈ 60 × (30 s + 1 s) ≈ 31 minutes inside one `with transaction():`

Consequences beyond latency:

- Nothing writes `.watchdog_status.json` during the wait, so `assess_runtime_health`
  reports `watchdog_stale` — the operator sees "watchdog died" rather than "waiting on lock".
- Every writer inherits it: `enqueue_mutation`, `claim_mutation_outbox`, `tool_ingest`,
  `tool_delete`, `tool_gc`, `tool_timeline`, `indexer`, `embedding_scheduler`.
- The retry loop also does not cover `conn.commit()`; if the commit fails the exception
  escapes without a rollback, leaving the connection inside an open transaction, and the
  *next* `BEGIN IMMEDIATE` on that connection raises `cannot start a transaction within a
  transaction` — a misleading error for what is really a stuck lock.

Fix: monotonic deadline + jittered backoff + `PRAGMA busy_timeout` scaled to the remaining
budget + a typed `DatabaseLockTimeout`; roll the connection back when `commit()` fails.

### F2 — P1 — canonical writes are not `fsync`ed before `os.replace` (durability)

`grep -rn fsync vector_lake/` → 0 hits, across five temp-file-then-rename sites:

| Site | Payload |
|---|---|
| `wiki_utils.atomic_write_text` (`:327-331`) | every wiki markdown page |
| `indexer._write_json_payload` (`:250-266`) | `index.json` |
| `indexer._replace_with_retry` (`:1219-1232`) | `index.json`, `claim_graph.json` |
| `native_llm.py:106` | task packets |
| `tool_ingest.py:600` | processing file registry |

`os.replace` is atomic with respect to *readers*, and the code correctly retries
`PermissionError` on Windows. But without `flush()` + `fsync()` the new inode's data may not
be durable when the directory entry is swapped, so a power loss can leave a **zero-length or
torn** `index.json` or wiki page while the previous content is already unlinked.

The markdown wiki is the human-visible canonical layer of this system; `SafeWriteError`
already guards *logical* loss (compiled-truth / evidence-timeline item counts) but nothing
guards *physical* torn writes.

Fix: `handle.flush(); os.fsync(handle.fileno())` before `os.replace`, and fsync the parent
directory on POSIX. Cost is one syscall per file; measurable only on bulk ingest.

### F3 — P1 — the idempotency unique indexes do not exist on the live database (integrity)

`db_store.py:520-534` (mutation_outbox) and `:686-703` (jobs) both swallow
`sqlite3.IntegrityError` and log "Skipping …". The live DB satisfies the trigger condition:

```
idx_mutation_outbox_idempotency  -> SKIPPED
duplicate idempotency_key groups -> 6
  3aa404ec…b4821  ids 26053,26046  completed,superseded
  555dc4ae…b83e   ids 17357,13142  completed,completed
  6514948d…b6a    ids 11397,2803   completed,completed
  7377dd8d…99e    ids 17361,17348  completed,completed
  7b305c67…f38    ids 15136,558    completed,completed
  83ec1d26…8bc    ids 11445,2806   completed,completed
jobs duplicates -> none
```

So on the live database there is currently **no unique index at all** on either table;
`enqueue_mutation` (`db_store.py:1007-1019`) is protected only by the `BEGIN IMMEDIATE`
write lock covering its `SELECT`-then-`INSERT`.

The skip is a deliberate availability trade, and it is the right *default*. What is missing
is the second half: the guarantee can be restored **without deleting audit history** by
falling back to a partial unique index over in-flight rows only —

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_mutation_outbox_idempotency_active
ON mutation_outbox(idempotency_key)
WHERE idempotency_key IS NOT NULL AND status IN ('pending','processing')
```

which is exactly the population the concurrent-enqueue race can produce. All 6 duplicate
groups are terminal, so this index would be created successfully on the live DB today.

3. The last sample records `projection_object_bytes` 6.40 GB against

This is the project's largest architectural risk: persisted contracts whose producer *and*
consumer were both lost, invisible from inside the current tree. It is not fixable by
refactoring — it needs a decision about which external state is still authoritative.

### F8 — P3 — scheduler can silently skip a day of maintenance

`watchdog_app.scheduled_lint_loop` (`:440-486`) fires only when
`tm_hour in (10, 23) and tm_min == 0`, sampled every 30 s. If the loop is inside its own
60 s `time.sleep` at that instant, or the process was restarted, the daily lint **and** the
`PRAGMA wal_checkpoint(TRUNCATE)` that is the only periodic WAL truncation are skipped for
the day. There is no catch-up predicate on last-success timestamp.

### F9 — P3 — style / dead indirection
86 ruff findings, all `E701`/`E402`. One is a genuine readability defect:
`wiki_utils.py:421` places `from typing import TypedDict, List` mid-module, after executable
code. `defense_hook.py` (21 lines) is a single-symbol pass-through over `schema_validator`
while participating in the 7-module SCC.

### F10 — P1 (reliability) — the write gate read a stale wiki key set (found late; see §7.9)

`runtime_health._wiki_keys_cached` memoised the wiki page-key set on the containing
directory's `(st_mtime_ns, st_size)`, on the stated assumption that "the wiki key set only
changes when the directory entries change, which is exactly what the directory timestamp
tracks". NTFS does not honour that:

```
dir stamp before creating a file: (1789601138588298000, 0)
dir stamp after  creating a file: (1789601138588298000, 0)   <- unchanged
300 rapid creates -> 42 distinct stamps
```

So `assess_runtime_health()` — which the canonical write gate calls — could report no
`projection_drift` for a page that had just been added or deleted. Fix and measurements in
§7.9: `os.scandir` at 30.9 ms versus the cache's own 506 ms miss path, for an identical key
set, and no memoisation.

The repository was under concurrent write by two other live Pi sessions when S1 was
being staged. That is recorded here because it is why the analysis and the
implementation are separated in time, and because the evidence pattern is worth
keeping. Evidence at the time:


Both are mid-implementation of the `memory_gram_index` feature. Their uncommitted write-set
overlaps every file S1–S4 would touch:

```

 M vector_lake/tool_search.py         M vector_lake/indexer.py
 M vector_lake/cli_app.py             M vector_lake/mcp_server.py

```

Their changes are uncommitted, so there is no commit to fork from that would produce a
mergeable patch — a worktree would branch off stale `HEAD` (`ec2d4dc`) and conflict on merge.

Per the execution contract's single-writer rule for a shared resource, mutating these files
then would have corrupted in-flight work and made their test runs unreliable. **The first
pass therefore stopped before the first write.**

That conflict was resolved when those sessions committed their work as `4ab152f`
("Read paths: sub-second search/query/timeline at 8.5k pages"), `07d7ad6` and `97dbf1f`.
S1–S6 were then applied on `main` on top of that commit. Keep the discipline anyway:
this repository has three writers, so re-check `git status --porcelain` and the target
file's mtime before staging a batch.

## 7. Implemented on `main`, 2026-09-17

Base commit `97dbf1f`. Ruff `F`-class clean on every touched file; `python -m compileall -q vector_lake` clean.

| | Tests | Wall |
|---|---|---|
| Before | 487 passed | 26.0 s |
| After | **535 passed** | 27.1 s |

New tests: `test_durable_writes.py` (7), `test_idempotency_index.py` (8), `test_scheduled_lint.py` (11), `test_backup_retention.py` (16), `test_db_transactions.py` (+3).

### 7.1 S1 — bounded write-lock wait (`db_store.py`)

`transaction()` no longer retries 60 times against a 30 s busy timeout (worst case ≈ 31 min).
It now has `BEGIN_LOCK_BUDGET_SECONDS = 90.0`, `BEGIN_LOCK_MAX_ATTEMPTS = 8`, jittered
exponential backoff, `PRAGMA busy_timeout` re-armed to the *remaining* budget before each
attempt and restored to `DB_BUSY_TIMEOUT_MS` afterwards, and raises the typed
`DatabaseLockTimeout` on exhaustion.

A failed `conn.commit()` now rolls back. Before, the exception escaped with the transaction
still open and the next `BEGIN IMMEDIATE` on that connection raised `cannot start a
transaction within a transaction` — a misleading error for a stuck lock. The duplicated
`_INIT_LOCK` and the unused `_INIT_DB_DONE` are gone.

Evidence — 3 tests: a held lock raises **inside** the budget (`1.0 <= elapsed < 10.0` against
a 2 s budget, versus ~31 min before), a lock released mid-retry still succeeds and restores
the default patience, and a failing commit rolls back leaving the connection reusable.

### 7.2 S2 — `fsync` before every publish (`wiki_utils.py`, `indexer.py`, `native_llm.py`, `tool_ingest.py`)

New `wiki_utils.flush_durable(handle)` and `wiki_utils.fsync_directory(path)`, applied to all
five temp-file-then-`os.replace` sites: `atomic_write_text`, `_write_json_payload`,
`_write_json_stage`, the `index.json` / `claim_graph.json` publish pair, `_replace_with_retry`,
the `native_llm` task packet and the ingest in-flight ledger.

Cost on a 5 KB wiki page: **2.071 ms → 3.216 ms**, i.e. +1.15 ms per canonical write
(≈ +9.7 s on a full 8 488-page rebuild; 1–2 ms per incremental ingest event).

Evidence — 7 tests assert the ordering directly: at the moment `flush_durable` runs, the
destination still holds the **previous** content and the temp file already holds the **new**
one. Not verified: no crash/power-loss injection was run. The claim is "synced before the
entry is swapped", not "a torn write was reproduced and fixed".

### 7.3 S3 — idempotency uniqueness actually enforced (`db_store.py`, `tool_doctor.py`)

`_ensure_idempotency_index` degrades instead of giving up: it tries the full unique index and,
on duplicate history, creates `<index>_active` over non-terminal rows
(`idempotency_key IS NOT NULL AND COALESCE(status,'') NOT IN
('completed','finalized','cancelled','superseded')`). The predicate is written as "not
terminal" so a status added later is protected by default rather than falling outside the
index. New `idempotency_index_state()` and `repair_idempotency_keys(table, dry_run=True)`,
which clears only the **redundant** keys (all but the lowest `id`, the row
`enqueue_mutation` already treats as canonical) and then reclaims the full index — no audit
row is deleted.

Live result: all 6 duplicate groups are terminal, so the full index stays unavailable, but
`idx_mutation_outbox_idempotency_active` was created and `doctor` now prints
`[OK] Idempotency Index: jobs=full(dups=0), mutation_outbox=active(dups=6)`.

**Side effect to disclose:** running doctor (or any command) once against the live DB created
that new partial index in `MEMORY/wiki/.meta/vector_lake.db`. Additive and non-destructive —
it is exactly what the next command would have done anyway.

### 7.4 S5 — backup retention with a real bound (`backup_retention.py`, `watchdog_app.py`, `tool_doctor.py`)

New module `vector_lake/backup_retention.py`: `scan_backups`, `plan_backup_retention`,
`prune_backups(..., dry_run=True)`. A `.db.bak` and its `-wal`/`-shm` sidecars form one
indivisible unit; a `create_maintenance_backup` directory is another. Anything unrecognised is
reported and **never** pruned. The newest copy is never a candidate, every candidate is
re-checked to be a direct child of the root, symlinks are refused, and a doctored plan
pointing outside the root is rejected.

Bounds: `VECTOR_LAKE_BACKUP_KEEP` (default 3), `VECTOR_LAKE_BACKUP_MAX_BYTES` (default 12 GiB).
Enforced from `scheduled_lint_loop`, next to the WAL checkpoint — the one place that already
does housekeeping — and reported by `doctor`.

> **Enforcement caveat (R12).** `doctor` reports `watchdog_stale:68387`, i.e. the watchdog
> is **not running** on this host. S5's prune and S6's catch-up both live in the watchdog's
> scheduled loop, so neither bound is enforced until it is started. The retention plan is
> readable at any time without it (`plan_backup_retention`), and today it would remove
> nothing anyway.

Live result: 3 entries, **10.70 GiB, 0 removable**. The shipped bound is a guard, not a purge.
The 388 MB freelist was deliberately **not** touched (see §6 R5). Evidence — 16 tests.

### 7.5 S6 — scheduler catch-up (`watchdog_app.py`)

The `tm_hour in (10, 23) and tm_min == 0` window (sampled every 30 s) is replaced by
`scheduled_lint_occurrence()` plus a persisted marker in `.meta/.scheduled_lint_state.json`.
The loop runs when the most recent scheduled instant has not completed, so a restart or a slow
tick catches up instead of silently dropping the day's lint — and with it the only periodic
`PRAGMA wal_checkpoint(TRUNCATE)`. A week of downtime still yields exactly one run; a failed
run is not recorded, so it retries on the next tick.
`VECTOR_LAKE_IGNORE_SCHEDULED_LINT_STATE=1` forces a re-run. Evidence — 11 tests, including
the loop's end-to-end trigger and its no-re-run path.

### 7.9 Follow-up batch — CLI/MCP entry points, and the two defects that found

`prune_backups` and `repair_idempotency_keys` are now reachable from both surfaces, and
building the tests for that found two real bugs in the stage-3 repair plus a third defect in
the write gate.

**Entry points** (new `vector_lake/tool_maintenance.py` holds the text; the repair logic stays
presentation-free):

| Surface | Command / tool | Mutating branch |
|---|---|---|
| CLI | `cli.py backup-retention [--keep N] [--max-bytes N] [--apply]` | `--apply` |
| CLI | `cli.py idempotency-status` | read-only |
| CLI | `cli.py repair-idempotency [--table mutation_outbox\|jobs] [--apply]` | `--apply` |
| MCP | `backup_retention_report(keep, max_bytes, dry_run=True)` | `dry_run=False` |
| MCP | `idempotency_index_status()` | read-only |
| MCP | `repair_idempotency_keys(table, dry_run=True)` | `dry_run=False` |

Both underlying functions keep `dry_run=True` as their own default, and a test asserts that
across every layer, so no surface can reach a mutating branch by accident.

**F10a — `repair_idempotency_keys` crashed on `jobs` (found by the surface tests).** The
predicate ``id NOT IN (SELECT MIN(id) ...)`` hardcoded `id`, but `jobs` is keyed by
`job_id`. It raised `no such column: id` on the first call against a clean `jobs` table. The
primary-key column is now part of `_IDEMPOTENCY_INDEXES`.

**F10b — the same repair coerced the primary key to `int`.** `jobs.job_id` is a hex string,
so the repair raised `invalid literal for int() with base 10: 'job1'`. The result field
`redundant_ids` is renamed `redundant_keys` and the values are carried through untyped.
Both bugs were in code that had passing tests, because the stage-3 tests only exercised
`mutation_outbox` — the `jobs` path was untested.

**F10 — the same class of defect, in the write gate.**
`runtime_health._wiki_keys_cached` memoised the wiki page-key set on the containing
directory's `(st_mtime_ns, st_size)`, justified by "the wiki key set only changes when the
directory entries change, which is exactly what the directory timestamp tracks". That is
false on NTFS. Measured on this host:

```
dir stamp before: (1789601138588298000, 0)
dir stamp after creating a file: (1789601138588298000, 0)   <- unchanged
300 rapid creates -> 42 distinct stamps
```

So `assess_runtime_health()` could report no `projection_drift` for a page that had just been
added or deleted, silently blinding the drift signal the write gate reports. It also explains
an intermittent failure of `test_projection_drift_is_reported_but_does_not_block_its_own_repair`
seen once during this work.

Fix: `wiki_utils.wiki_page_keys()` scans with `os.scandir` and callers no longer memoise it.
The scan is also **16× cheaper** than the cache's own miss path, measured on the live
8 488-page wiki:

| Implementation | p50 | key set |
|---|---|---|
| `glob` + `Path.is_file` (previous cache-miss path) | 506.0 ms | 7 178 |
| `os.listdir` + `isfile` | 424.2 ms | 7 178 |
| `os.scandir` (now) | **30.9 ms** | 7 178 (identical) |

`tool_doctor` reused the same 506 ms glob per run and now calls the shared helper. So this is
both a correctness fix and a 16× reduction in the health check's cost.

Guard: `tests/test_wiki_page_keys.py` (6 tests) pins "a new page is visible without any sleep
and without any directory-stamp change" and "repeated reads are never stale".

**Retention semantics changed** while wiring the CLI: `keep_count` is now a *ceiling* (older
entries are always removed) and `max_bytes` is a second ceiling that can pull the retained set
*below* `keep_count` when the newest copies alone exceed it, but never below one copy. The
previous reading — `keep_count` as a floor with `max_bytes` allowing extra retention — made
`--keep 2` silently do nothing while the default 12 GiB budget had room. Against the live tree
both readings agree: 3 entries, 10.70 GiB, 0 removable, because 10.70 GiB < 12 GiB.

The 12.0 GiB default was chosen above the current footprint on purpose: it is a guard that
fires when growth is abnormal (the observed trend was a doubling per day), not a purge that
acts on the current state.
