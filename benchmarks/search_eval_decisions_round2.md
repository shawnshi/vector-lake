## 4. 样本量（按功效算，不拍脑袋）

第一轮观测：差值 SD ≈ 0.259–0.305，效应/噪声比 0.12–0.17。
80% 功效、α=0.05 双侧下，**能检出的最小效应**为 `MDE = (z₀.₉₇₅ + z₀.₈) · SD / √n`：

| n | MDE (SD=0.26) | MDE (SD=0.29) | MDE (SD=0.31) |
|---|---|---|---|
| 150 | 0.0595 | 0.0663 | 0.0709 |
| 200 | 0.0515 | 0.0574 | 0.0614 |
| 250 | 0.0461 | 0.0514 | 0.0549 |
| **300** | **0.0421** | **0.0469** | **0.0501** |
| 523 | 0.0319 | 0.0355 | 0.0380 |

反过来算，要让观测到的效应（≈ +0.045）以 80% 功效被检出，需要 **n ≈ 272–523**（随标注集不同）。

**推荐：n = 300 条新查询 + 最小效应量 +0.05。** 两者是自洽的 —— n=300 在 SD=0.29–0.31 时的 MDE 正好 ≈ 0.047–0.050，即**在门槛处刚好有 80% 功效**。
若坚持 n=150，则效应量必须放宽到 **+0.07**，否则规则按设计就不可能通过。

### 事故与协议修正（2026-09-21）

**事实**：`benchmarks/search_eval_labels.jsonl`（第一批已闭合记录，HEAD 40 行）在本次运行中被**改写为 76 行**。已 `git checkout --` 回滚（现为 40 行），覆盖版本留档于 `scratch/INCIDENT_forked_child_overwrote_round1_labels.jsonl`。

**原因**：本次 15 个判定 child 跑在 **`context: fork`**（继承父会话上下文），不是 fresh。证据在 d2-s4 的推理轨迹里：它没有做自己的分片判定，而是复述并执行**父代理的编排计划**——“the user asked to 继续处理 … the next step (step 3) is to run the evaluation and produce a verdict”，并计划改写第一批标注文件与 `analyze_judge_c.py`。另一个 child（d1-s5）也在复述父会话的进度判断。

fork 上下文同时造成两个后果：
1. **判定独立性被污染** —— child 知道本实验的假设与历史结果，不再是只看到盲判池的判定者；
2. **角色混淆** —— 带 `write` 权限的 child 会去执行父代理的计划，而不是它被分派的那一个任务。

**协议修正（强制，适用于以后所有判定批）**：
1. 判定 child **必须 `context: "fresh"`**。任务文本已自带完整判定标准与格式要求，不依赖继承上下文；fresh 同时消除上述两种后果。
2. 判定 child 的输出路径一律限于 `scratch/` 且以 `labels_*` 前缀，**禁止其触碰 `benchmarks/`**。
3. 每批结束后父代理必须 `git status` 核对仓库。但“非我写入”不等于“事故”：本机同时跑着**其它授权的 Pi 会话**——本次就碰到一个（`embedding_scheduler.py`、`indexer.py`、`periodic_catch_up.py`、`test_embedding_scheduler.py`、`README.md` 在同一分钟内被改，内容是给兜底循环加 `VECTOR_LAKE_CATCHUP_EMBEDDING_BATCH` 补向量的完整功能，带测试与 README 登记）。先后顺序是：先判定它是不是并发授权写入者（`sessions/` 下有没有新会话、mtime 是否同分钟、改动是否成体系），再决定：
   * 是 → **不因它而回滚**（保留他人脏工作区），只核对自己的提交范围干净；
   * 不是 → 按事故处理：回滚、留档、记录。
4. 提交一律按路径显式 `git add -- <path>`，绝不用 `-A`/`.`，以免把并发写入者的改动或本实验的文件扫进对面。

### 判定实现 v2 的失败（2026-09-21，实测）

fresh 上下文修好之后，判定仍未跑通。实测事实：

**v2（每个 child 一个 250KB 分片，共 3 判定者 × 5 分片）**：9 个已 spawn 的 child **全部撞上运行时的 30 分钟子代理上限**（`Subagent timed out after 1800000ms`），零产出、`changed tracked files: none`，共烧掉约 220 万 token；每个 workflow 只 spawn 了 3 个 child（s4/s5 根本未启动）。

不是配额、不是网络、也不是判定逻辑。逐个看 transcript：

* 每个 child 有 26–44 次成功调用、17 万–31 万 token，**全部消耗在反复 `bash` 进出分片**：一条命令拉回一整段页面正文，再换一条、再换一条；
* 两个 child 自己动手把分片压了一遍，在 scratch 里留下 `pool_r2_shard2_compact.txt`、`pool_r2_shard4_compact.txt` —— 它们试图自行缩小仪器。

**根因：输入单位太大。** 分片约 3.7KB/查询 × 67 查询 ≈ 250KB（约 6–10 万 token），一个 child 在 30 分钟内既读不完也写不出来。这不是判定者的能力问题，是我给的工作单位错了。

### 顺带修掉的两处"登记与实现不一致"

## 这份结论真正的证据强度（如实记账）

1. **有效样本是 65 / 62，不是 300。** harness 那道"确认查询数"数的是"有标签的查询"（333 全数通过），与"池里有页可找的查询"不是一回事。本节并列给出两个数，前者不顶替后者。
2. **80% 的查询在候选池里没有任何"主体对得上"的页**，而候选池 = 两路各 top-5 的并集 —— 这是对 **top-5 召回**的直接测量，不是语料覆盖问题（向量已 100% 覆盖 7175/7175 页，实测）。
3. **主判定者与本批另外两位不一致**（kappa 0.35/0.40 vs 0.68）。本轮结论因此更要读作"**在这把最严的尺子下，跨 333 条查询也没量出 +0.05**"，而不是"融合改动已经被证明无用"。

## 语料漂移（2026-09-22 发现，必须与本批结论一起读）

**事实**：本批候选池冻结于 `2026-09-22 08:08`，而计分用的 run 在当晚才跑。两者之间，向量兜底补齐把这个库的向量从 **2602 补到 7175**。实测差异：

| | |
|---|---|
| 今天 k=5 返回、但不在冻结池里的页键 | **664** |
| 在冻结池里、但今天 k=5 不返回的页键 | **1348** |
| 集合不一致的查询 | **330 / 333** |
| 那 664 个新页键里经向量这一路进来的 | **97.6%**（vec 640 + both 8）|

**后果分两层**：

- **相对比较仍然成立**：sum 与 rrf 用的是同一批 run、同一批标签，两边被同样对待 → "rrf 在主指标上没达到 +0.05" 这个判定不受影响。
- **绝对水平与覆盖率数字不成立**：`nDCG@5 ≈ 0.12` 与"80% 的查询池内没有相关页"是**旧索引**的属性。按今天的索引，同样那 268 条里 top-5 已能召回 **42（sum）/ 44（rrf）** 条此前"零相关"的查询、top-20 为 **50** 条。

**结构性修复**：`search_replay.py` 现在计算并记录**语料指纹**（页面数、有向量的页键集合、全文索引规模）；run 记录带 `corpus`，标签文件可带 `# corpus <指纹>` 头；两次 run 语料不同则 `--compare` **拒绝比较**，标签语料与当前语料不同则回放时**显式警告**并把两个指纹都写进 run。四份标签已加 `# corpus pre-2026-09-22-vector-backfill`。

**若要拿到当前语料的绝对值**，需要按今天的索引重判一次候选池（= 一轮新的标签采集），而不是改本批的数字。
